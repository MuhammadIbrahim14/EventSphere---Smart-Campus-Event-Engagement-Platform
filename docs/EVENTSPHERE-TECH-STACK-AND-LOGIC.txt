PART 1 — BIG PICTURE (30-SECOND ELEVATOR ANSWER)
================================================================================

WHAT IS EVENTSPHERE?
  A web application for campus events. Four user types:
  Guest (public visitor), Student (campus user), Organizer (event creator),
  Admin (platform owner). Students discover events, register, pay in PKR via
  Stripe, get QR passes, attend, give feedback, earn certificates. Organizers
  create events. Admin approves events, manages users, settles money.

ARCHITECTURE IN ONE LINE:
  React website (frontend) talks to Supabase (backend database + auth)
  and Stripe (payments) and EmailJS (emails). Hosted on Netlify.

WHY NOT TRADITIONAL BACKEND (Express/PHP)?
  Supabase gives us database, login, security rules, and server functions
  without writing a separate Node server. Faster for a student project,
  still production-grade. Our "server" folder is actually API helper code
  that runs inside the browser and calls Supabase directly.

2.1 FRONTEND — WHAT USER SEES
--------------------------------------------------------------------------------

REACT (v19)
  WHAT: JavaScript library to build UI using reusable "components"
  WHY: Industry standard, component-based, huge community
  IN PROJECT: Every screen is a React component (buttons, forms, dashboards)
  EXAMPLE: StudentDashboard.jsx is one big component with smaller pieces inside

VITE (v8)
  WHAT: Build tool — runs dev server and bundles app for production
  WHY: Very fast hot reload during development; modern replacement for CRA
  IN PROJECT: npm run dev starts Vite; npm run build creates dist/ folder
  ANALOGY: Vite is like a factory that packages your React app for browser

WOOTER (not "router" typo — library name is Wouter)
  WHAT: Tiny client-side routing library for React
  WHY: Lighter than React Router; we only need simple URL → page mapping
  HOW: When URL is /student/discover, Wouter shows Discover page component
  VS REACT ROUTER: Both do same job; we chose Wouter for size/simplicity
  IN PROJECT: All routes defined in App.tsx using Wouter's Route and Switch
  TEACHER MAY ASK: "What is routing?"
    ANSWER: Routing means showing different pages based on URL without
    full page reload. Single Page Application (SPA) — one HTML file,
    JavaScript swaps content.

TAILWIND CSS (v4)
  WHAT: Utility-first CSS framework (classes like flex, p-4, text-white)
  WHY: Fast styling without writing separate CSS files for everything
  IN PROJECT: index.css + eventsphere-design-system.css + role skins

TANSTACK REACT QUERY
  WHAT: Library for fetching/caching server data in React
  WHY: Avoids re-fetching same data; handles loading/error states
  IN PROJECT: Wrapped around App in QueryClientProvider

FRAMER MOTION
  WHAT: Animation library for React
  IN PROJECT: Smooth transitions on auth screens, modals, campus boot loader

LUCIDE REACT
  WHAT: Icon pack (calendar, user, settings icons)
  IN PROJECT: Sidebar navigation, buttons, dashboards

QR CODE LIBRARIES
  qrcode.react — generates QR image for student/guest passes
  html5-qrcode — camera scanner for organizer attendance check-in

CLSX + TAILWIND-MERGE
  WHAT: Small utilities to combine CSS class names safely
  IN PROJECT: Used in design system components

2.2 BACKEND — SUPABASE (THE BRAIN)
--------------------------------------------------------------------------------

WHAT IS SUPABASE?
  Open-source "Backend as a Service" — Firebase alternative built on Postgres.
  Gives: Database, Authentication, File Storage, Realtime, Edge Functions.
  We don't host our own MySQL/PHP server — Supabase cloud hosts everything.

POSTGRESQL (Postgres) — MOST IMPORTANT DB CONCEPT
  WHAT: Relational database — data stored in TABLES with ROWS and COLUMNS
  WHY: Events, users, registrations are relational (event belongs to organizer,
       registration links student to event). SQL databases handle this well.
  VS MONGODB: Mongo is document/noSQL; we need strict relations and transactions
  IN SUPABASE: Postgres runs behind the scenes; we access via Supabase client
  TEACHER MAY ASK: "What is SQL?"
    ANSWER: Structured Query Language — language to read/write database tables.
    SELECT gets data, INSERT adds, UPDATE changes, DELETE removes.
  TEACHER MAY ASK: "What is a table?"
    ANSWER: Like Excel sheet — columns are fields (name, email), rows are records.

ROW LEVEL SECURITY (RLS)
  WHAT: Postgres feature — each row has security rules per user
  WHY: Student A cannot see Student B's registrations. Organizer only sees
       own events. Enforced at DATABASE level, not just frontend hiding.
  EXAMPLE: profiles table — you can only UPDATE your own row unless admin
  THIS IS A STRONG DEFENSE POINT IN VIVA

SUPABASE AUTH
  WHAT: Built-in login system (email + password, sessions, JWT tokens)
  HOW: User signs up → Supabase creates auth.users entry → we create profiles
       row with role (student/organizer/admin/guest)
  SESSION: JWT token stored in browser; sent with every API request
  OTP: We added custom email OTP via EmailJS + database RPC functions

SUPABASE REALTIME
  WHAT: Live updates when database changes (like WebSocket)
  IN PROJECT: Dashboards refresh when new registration or event approval happens

SUPABASE STORAGE
  WHAT: File hosting (images, certificates, avatars)
  BUCKET: event-media — banners, gallery photos, generated certificate PNGs

SUPABASE EDGE FUNCTIONS
  WHAT: Server-side TypeScript functions on Deno runtime (Supabase cloud)
  WHY NEEDED: Stripe secret keys CANNOT be in browser — must run on server
  OUR FUNCTIONS:
    create-checkout-session — starts Stripe payment
    confirm-checkout-session — verifies payment when user returns from Stripe
    stripe-webhook — Stripe calls this when payment completes (backup)
    refund-deposit — organizer/admin refunds deposit or full payment
    send-event-reminders — cron job for 12-hour event reminders

RPC (Remote Procedure Call)
  WHAT: Custom database functions we call by name from frontend
  WHY: Complex logic (seat counting, registration) runs safely in Postgres
  EXAMPLES: register_for_event, finalize_registration_payment, settle_registration_earnings

2.3 PAYMENTS — STRIPE
--------------------------------------------------------------------------------

WHAT IS STRIPE?
  Payment gateway — handles card processing securely (PCI compliant)
  We use SANDBOX/TEST mode — fake cards, no real money

STRIPE CHECKOUT
  WHAT: Hosted payment page — user redirected to Stripe, pays, returns to our site
  WHY: We don't handle card numbers ourselves (security + legal)

FLOW:
  1. Student clicks Pay on paid event
  2. Frontend calls Edge Function create-checkout-session
  3. Edge Function creates Stripe session, returns URL
  4. Browser redirects to Stripe
  5. Student pays (test card 4242...)
  6. Stripe webhook OR confirm-checkout-session marks registration as paid
  7. finalize_registration_payment RPC updates DB + splits commission

CURRENCY: PKR (Pakistani Rupees) — not USD

COMMISSION MODEL (BUSINESS LOGIC):
  Student pays 100% (entry fee; deposit separate)
  Platform keeps 20% of entry fee
  Organizer gets 80% — held until admin marks "settled" (offline payout)
  Security deposit is NOT part of commission split — refunded on attendance

--------------------------------------------------------------------------------
2.4 EMAIL — EMAILJS
--------------------------------------------------------------------------------

WHAT IS EMAILJS?
  Service to send emails from frontend using templates (no own SMTP server)

TWO TEMPLATES (IMPORTANT — don't mix):
  1. OTP template — signup verification, forgot password (contains OTP code)
  2. Notify template — registration confirmed, payment receipt, reminders

WHY NOT SUPABASE BUILT-IN EMAIL ONLY?
  We use custom OTP flow stored in database + EmailJS for delivery control

PART 4 — USER ROLES & PERMISSIONS (LOGIC)
================================================================================

ROLE MAPPING (Database → UI):
  profiles.role = 'user'      → Student panel (/student/*)
  profiles.role = 'organizer' → Organizer panel (/organizer/*)
  profiles.role = 'admin'     → Admin panel (/admin/*)
  profiles.role = 'guest'     → Guest hub (/guest/*)
  Not logged in               → Public pages only

SIGNUP RULE:
  New account is ALWAYS student (or guest if ?intent=guest in URL)
  Organizer and Admin assigned ONLY by Admin in user management

GUEST vs STUDENT (IMPORTANT DISTINCTION):
  Guest = public attendee, separate seat pool (public_capacity on event)
  Student = campus user, uses main capacity
  Guest does NOT get certificates (students only)
  Both can have QR passes for entry

AUDIENCE BUCKETS:
  Registration stored with audience type — student or public
  Roster shows "Campus students | Public guests" separately

PART 6 — CORE BUSINESS LOGIC FLOWS (STEP BY STEP)
================================================================================

--------------------------------------------------------------------------------
6.1 EVENT LIFECYCLE
--------------------------------------------------------------------------------
  Organizer creates event → status: pending
  Admin approves → status: approved → visible in Discover
  Students/guests register → registrations row created
  Event happens → attendance marked
  Event ends → feedback, certificates
  Organizer earnings → admin settles offline

--------------------------------------------------------------------------------
6.2 REGISTRATION + CAPACITY
--------------------------------------------------------------------------------
  register_for_event RPC runs in Postgres (not browser math)
  Checks: event approved, not full, not already registered, registration open
  Two pools: capacity (students) + public_capacity (guests)
  waitlist_enabled: if full, status = waitlisted instead of rejected
  cancel_registration may promote next waitlisted user

--------------------------------------------------------------------------------
6.3 PAYMENT FLOW (PAID EVENT)
--------------------------------------------------------------------------------
  1. start_paid_registration RPC reserves slot, calculates fee (early bird, promo)
  2. create-checkout-session Edge Function talks to Stripe
  3. User pays on Stripe hosted page
  4. stripe-webhook receives checkout.session.completed
  5. finalize_registration_payment stamps: paid, platform_fee (20%), organizer_share (80%)
  6. confirm-checkout-session is backup if user returns before webhook

--------------------------------------------------------------------------------
6.4 DEPOSIT REFUND LOGIC
--------------------------------------------------------------------------------
  Security deposit = separate from entry fee
  Student cancels early enough → deposit refunded via refund-deposit function
  Student no-show / late cancel → deposit forfeited (mark_registration_forfeited)
  Student attends (Present) → organizer/admin triggers deposit refund
  Event cancelled → full refund for all paid registrations

--------------------------------------------------------------------------------
6.5 ATTENDANCE + QR
--------------------------------------------------------------------------------
  Student pass QR contains signed payload (registration + event IDs)
  Organizer scans with camera (html5-qrcode) → marks attendance row
  Station poster QR links to /checkin/:eventId?token=... for self check-in
  Certificate only issued to students marked Present

--------------------------------------------------------------------------------
6.6 COMMISSION & SETTLEMENT
--------------------------------------------------------------------------------
  NOT Stripe Connect — platform holds money in Stripe; organizer paid offline
  settlement_status on registration: held → settled
  Admin clicks Mark Settled after bank/cash payout to organizer
  Demo withdraw: organizer requests → admin approves in Payments tab

--------------------------------------------------------------------------------
6.7 AUTH & SECURITY
--------------------------------------------------------------------------------
  JWT session from Supabase Auth
  profiles table linked to auth.users by UUID
  RLS ensures users only access own data
  Edge Functions use service_role key for admin Stripe operations (server only)
  email_verified gate — some actions blocked until OTP verified

--------------------------------------------------------------------------------
6.8 EMAIL NOTIFICATIONS
--------------------------------------------------------------------------------
  OTP flow: database generates code → EmailJS sends
  Campus notify: registration confirm, payment receipt, waitlist, reminders
  send-event-reminders Edge Function: cron finds events in 12h → student_notices

--------------------------------------------------------------------------------
6.9 THEME & DESIGN SYSTEM
--------------------------------------------------------------------------------
  themeEngine stores hex colors in platform_settings
  CSS variables on :root — all components use tokens
  Theme Studio admin UI edits colors live
  Certificates pick up theme colors when generated to canvas PNG

--------------------------------------------------------------------------------
6.10 REALTIME UPDATES
--------------------------------------------------------------------------------
  useRealtimeTables subscribes to Postgres changes
  When admin approves event, organizer dashboard updates without refresh

PART 9 — COMMON TEACHER TERMS GLOSSARY
================================================================================

SPA          — Single Page Application; one HTML, JS changes views
API          — Application Programming Interface; how apps talk to server
REST         — Style of API using HTTP verbs (GET, POST); Supabase uses REST + RPC
JWT          — JSON Web Token; proves who is logged in
CRUD         — Create Read Update Delete
ORM          — Object-Relational Mapping; we use Supabase client not classic ORM
BaaS         — Backend as a Service (Supabase)
CDN          — Content Delivery Network (Netlify serves fast globally)
CORS         — Cross-Origin Resource Sharing; Edge Functions send CORS headers
Webhook      — Server calls OUR server when event happens (Stripe payment done)
Sandbox      — Test environment (Stripe test mode)
PKR          — Pakistani Rupee currency code
RLS          — Row Level Security in Postgres
RPC          — Call a function inside database by name
Edge Function— Small serverless function near user (Supabase/Deno)
Checkout     — Stripe hosted payment page
Deposit      — Refundable security amount separate from ticket price
Waitlist     — Queue when event full
CMS          — Content Management System (About/FAQ admin edit)
OTP          — One Time Password for email verification

PART 10 — WHAT WE DELIBERATELY DID NOT USE (AND WHY)
================================================================================

  No PHP / Laravel — chose modern JS full-stack with Supabase
  No separate Express server in production — Supabase + Edge Functions enough
  No Stripe Connect — simplified to platform holds, offline organizer payout

  No mobile app — responsive web works on phone browsers
